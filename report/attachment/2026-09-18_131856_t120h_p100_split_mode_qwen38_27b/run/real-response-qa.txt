**1. Why GPU GEMV is bandwidth-bound:**

GEMV is y = Ax where A is an M×N matrix and x is an N×1 vector. The computational work is O(M*N) multiply-accumulate operations. But the memory access pattern is:
- Read the entire matrix A: M*N elements (each of size e.g. 2 bytes for fp16, or 0.5 bytes for 4-bit quantized)
- Read the vector x: N elements
- Write the vector y: M elements

The arithmetic intensity (FLOPs / bytes) is very low. For a standard GEMV:
- FLOPs = 2*M*N (multiply + add)
- Bytes transferred ≈ M*N * element_size (dominated by reading A)

Arithmetic intensity = 2*M*N / (M*N * element_size) = 2 / element_size

For fp16: 2/2 = 1 FLOP/byte
For fp32: 2/4 = 0.5 FLOP/byte
For 4-bit quantized: 2/0.5 = 4 FLOP/byte

Compare to GEMM (matrix-matrix): arithmetic intensity is O(min(M,N,K)) which can be hundreds.

GPU has massive compute capability (e.g., A100: 312 TFLOPS fp16) but memory bandwidth is ~2 TB/s. The roofline model shows that GEMV operates far below the compute roofline and hits the bandwidth ceiling. You're spending most of your time waiting for data to arrive from HBM/DRAM, not actually computing.

The key insight: the matrix A is read once and each element is used only once (or a few times in a reduction). There's no data reuse across multiple operations. In GEMM, each element of A is reused N times (once for each column of B), giving high arithmetic intensity.

**2. Why quantization block memory layout changes effective bandwidth:**

When you quantize a matrix (e.g., for LLM inference), you group weights into blocks (e.g., 128 or 256 elements per block). Each block has:
- Quantized weights (e.g., 4-bit or 8-bit per element)
- A scale factor (e.g., fp16 or fp32)
- Possibly a zero-point

The key issue: when the GPU's memory subsystem fetches data, it works in cache line units (typically 128 bytes on NVIDIA GPUs, which is 32 sectors of 32 bytes each). 

If the quantization block layout is:
- All 128 4-bit weights packed into 64 bytes, followed by a 2-byte scale → the block is 66 bytes
- But the GPU fetches in 32-byte sectors or 128-byte cache lines

If blocks are laid out so that a single cache line (128 bytes) spans multiple quantization blocks, you waste bandwidth reading scale factors you don't need yet, or you read padding bytes.

More specifically:
- If 128 4-bit weights = 64 bytes, and you have a 2-byte scale, the total per block is 66 bytes
- If you pack blocks contiguously: 66, 66, 66... the cache line boundaries don't align with block boundaries
- The GPU might need to fetch 2 cache lines to get one full block, reading extra bytes

Better layout: align blocks to cache line boundaries. E.g., pad each block to 128 bytes, or interleave blocks so that a cache line contains exactly one block's worth of data.

Also, for the dequantization: you need to read the scale AND the quantized weights together. If they're far apart in memory (e.g., all scales in one array, all weights in another), you have two separate memory streams, doubling the effective bandwidth needed. If they're interleaved (block-local), one cache line fetch gets both.

Another aspect: with block quantization, the GPU's memory controller reads in fixed-size chunks. If your block size doesn't align with these chunks, you get "wasted" reads. The effective bandwidth (useful bytes / total bytes transferred) drops.

For example, if a cache line is 128 bytes and your block is 64 bytes of weights + 2 bytes scale = 66 bytes:
- Naive packing: 128 bytes fetched, 66 useful, 62 wasted → effective bandwidth = 66/128 ≈ 52%
- Padded to 128: 128 bytes fetched, 66 useful → same waste but at least aligned
- Better: pack 2 blocks per 128 bytes (132 bytes... doesn't fit)
- Best: use block size that divides evenly into cache line size
