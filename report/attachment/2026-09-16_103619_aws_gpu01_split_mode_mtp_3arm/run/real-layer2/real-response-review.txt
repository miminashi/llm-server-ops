## 1. 主張の根拠が測定に基づいているか

### 問題の構造

技術文書で最も多い致命的欠陥は、**「測定した」と書かれているが、実測値ではなく推定・外挿・一条件限定の値である**ことです。

### 具体的な反例

**反例 A：合成ベンチマークによる性能主張**

> 「我々のコンパイラ最適化は実行時間を 47% 短縮する（図 3）」

- **何が問題か**: 図 3 のデータが `fib(30)` 単体ループの 1 回実行で得られた値だった場合、これは「測定」ではなく「一条件の点取り」です。実際のワークロード（I/O 混在、分岐予測の崩壊、キャッシュミス）では効果が消滅するか逆転する可能性があります。
- **レビューでの確認点**:
  - 測定対象の分布（入力サイズ、分岐率、メモリアクセスパターン）が明示されているか
  - 実行回数と分散（平均 ± 標準偏差）が報告されているか
  - 比較対象（baseline）が同一条件で測定されているか（例: 両方 `-O2`、同一 CPU、同一 OS カーネル）
  - 統計的有意差（p-value 或いは信頼区間）が示されているか

**反例 B：Uptime / 可用性の測定**

> 「本システムの可用性は 99.99% である（Table 2）」

- **何が問題か**: 計測期間が 2 週間、かつ計測が「API エンドポイント 200 を返すか」のみで、内部データ整合性・レイテンシ SLA 超過・部分障害（1 レプリカダウン）が除外されている場合、「測定」は形式上行っているが、主張を裏付けていません。
- **レビューでの確認点**:
  - 計測期間が主張する SLO の意味論と一致するか（99.99% は年間 52.6 分以下のダウンを意味する）
  - 「アップ」の定義が多層（L4 / L7 / 機能レベル）で定義されているか
  - 計測の独立性（同一チームが設計・実装・計測していないか）

### レビューコメントの型

> 「図 3 の 47% 改善は N=1 の合成ケースに基づいています。実ワークロード（例: TPC-C、実トラフィック再生）での分布を提示するか、または主張を『この特定ケースでは』に限定してください。」
