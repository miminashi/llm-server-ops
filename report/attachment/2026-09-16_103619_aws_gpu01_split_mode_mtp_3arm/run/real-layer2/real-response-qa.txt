**1. Why GEMV is bandwidth-bound on GPU:**

GEMV is y = A*x where A is an m×n matrix and x is an n×1 vector. The operation count is 2mn FLOPs (multiply-accumulate for each element). The data that needs to be read is:
- Matrix A: mn elements (this dominates)
- Vector x: n elements
- Output y: m elements

So arithmetic intensity = 2mn FLOPs / (mn + n + m) bytes ≈ 2 FLOPs/byte (for large m, n).

Modern GPUs like A100 have ~312 TFLOPS FP16 and ~2 TB/s HBM2e bandwidth. The roofline crossover is at 312/2 = 156 FLOPs/byte. GEMV at ~2 FLOPs/byte is WAY below this, so it's firmly in the bandwidth-bound regime.

The key insight: for each element of A, you do 1 multiply + 1 add = 2 ops, but you have to read that element (and the corresponding x element). The compute per byte of data is extremely low. The GPU's massive compute units sit idle waiting for data to arrive from HBM.

In contrast, GEMM (matrix-matrix multiply) has arithmetic intensity O(k) where k is the inner dimension, so it can be compute-bound.

**2. Why quantization block memory layout changes effective bandwidth:**

When you quantize weights (e.g., to 4-bit or 8-bit), the weights are stored in blocks. The question is how these blocks are laid out in memory.

Consider a 4-bit quantization with block size 128. You have groups of 128 weights sharing a scale (and possibly zero-point). 

Memory layout options:
- **Interleaved/planar**: All 4-bit weights for a block are stored contiguously, then the scale, then the next block's weights, etc.
- **Packed**: Multiple 4-bit values packed into a single byte (2 values per byte)
- **Channel-last vs channel-first**

The key issue is DRAM access patterns:
- DRAM reads in bursts (e.g., 32 bytes or 64 bytes per access)
- If your data layout doesn't align with these burst boundaries, you waste bandwidth
- If a block's weights span across DRAM bank boundaries or row boundaries, you get extra latency
- If the scale/zero-point is stored separately from the data, accessing one requires two memory transactions instead of one

For example, with 4-bit weights:
- If you store 2 weights per byte, and the block is 128 weights = 64 bytes + scale (2 bytes float) = 66 bytes
- If the scale is at a different alignment, you might read 128 bytes of DRAM to get 66 bytes of useful data → 52% efficiency
- If you pack the scale into the same 64-byte or 128-byte line, you get full efficiency

Another aspect: in GPU, the memory coalescing unit (or L2 cache line) works at 32-byte or 128-byte granularity. If your quantized block doesn't align with these, you fetch more than needed.

Also, the "effective bandwidth" changes because:
- The theoretical bandwidth is, say, 2 TB/s
- But if you're only using 66 out of 128 bytes per DRAM access, effective bandwidth = 2 TB/s × (66/128) ≈ 1.03 TB/s
- The GPU's compute units are starved even though the DRAM is "working"

Another important point: with quantization, you need to dequantize on-the-fly. The dequantization requires reading the scale. If the scale is stored in a way that causes additional cache misses or DRAM accesses, the effective bandwidth for the actual weight data drops.

**3. When logical bytes vs actual DRAM transfer diverge:**

Logical bytes = the number of bytes the kernel "thinks" it's reading (e.g., m×n×4 bytes for a float matrix)
Actual DRAM transfer = what actually goes over the DRAM bus

They diverge when:

a) **Cache effects**: If data fits in L2 cache, DRAM traffic is less than logical bytes. But this is usually the "good" direction.

b) **Alignment and burst waste**: As mentioned above, if your access pattern doesn't align with DRAM burst size, you read more than needed. E.g., you want 66 bytes but DRAM gives you 128 bytes.

c) **Non-coalesced access**: If threads in a warp access non-contiguous addresses, each thread's access may trigger a separate DRAM transaction. 32 threads × 4 bytes = 128 bytes logically, but if scattered, could be 32 × 32 bytes = 1024 bytes actual.

d) **Read-modify-write for partial writes**: If you're writing less than a full cache line, the GPU may need to read the full line
