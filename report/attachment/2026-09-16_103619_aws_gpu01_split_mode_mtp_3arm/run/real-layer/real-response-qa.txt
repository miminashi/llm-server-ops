**1. Why GPU GEMV is bandwidth-bound:**

GEMV = General Matrix-Vector multiplication: y = A * x, where A is an m×n matrix and x is an n-dimensional vector.

The key insight is the arithmetic intensity (FLOPs per byte):
- FLOPs: 2*m*n (multiply + add for each element)
- Bytes loaded: m*n (the matrix) + n (the vector, negligible) ≈ m*n bytes (or less if quantized)
- Arithmetic intensity = 2*m*n / (m*n) = 2 FLOPs/byte

Compare with GEMM (matrix-matrix): y = A * B where A is m×k, B is k×n
- FLOPs: 2*m*k*n
- Bytes: m*k + k*n (roughly)
- Arithmetic intensity = 2*m*k*n / (m*k + k*n) ≈ 2*min(m,n) for square matrices

So GEMV has extremely low arithmetic intensity (~2 FLOPs/byte for FP32, or even less for quantized). The GPU has massive compute throughput (TFLOPs) but memory bandwidth is much lower (hundreds of GB/s to ~2TB/s for HBM). 

For a modern GPU like H100:
- Compute: ~990 TFLOPS FP16
- Memory bandwidth: ~3.35 TB/s (HBM3)
- Roofline: to saturate compute, you need 990e12 / 3.35e12 ≈ 295 FLOPs/byte

GEMV only provides 2 FLOPs/byte (FP32) or even less. So the GPU's compute units are mostly idle waiting for data. The bottleneck is memory bandwidth, not compute. That's "bandwidth-bound" (帯域律速).

**2. Why quantization block memory layout changes effective bandwidth:**

In quantized inference, weights are stored in blocks (e.g., group of 32 or 128 weights share a scale and zero-point). The memory layout matters because:

- GPU memory access is coalesced: threads in a warp access consecutive memory addresses for maximum bandwidth
- If quantization blocks are laid out so that a single thread (or warp) needs to access scattered addresses, you get poor coalescing
- For example, if you have [w0, w1, ..., w31, scale, zero] repeated, a warp loading 32 consecutive weights is fine. But if the layout is [w0, w32, w64, ...] (column-major within blocks) or if scales are interleaved differently, you might get:
  - Partial memory transactions (reading 128-byte cache lines but only using a fraction)
  - Multiple transactions for what should be one
  - Unaligned access penalties

More specifically:
- DRAM is organized in rows/columns, and the GPU memory controller fetches in fixed-size chunks (e.g., 32-byte or 128-byte sectors)
- If your quantization block size doesn't align with these fetch granularities, you waste bandwidth fetching data you don't need
- If multiple blocks' data is interleaved in memory, a single thread's access pattern might span multiple cache lines
- The "logical" data you need might be, say, 4 bytes of INT4 weights + 2 bytes of scale, but physically they're spread across two 128-byte DRAM lines, so you actually transfer 256 bytes

Example: Suppose you have 32 INT4 weights (16 bytes) + 1 FP16 scale (2 bytes) + 1 FP16 zero (2 bytes) = 20 bytes per block. If blocks are packed contiguously: [16B weights][2B scale][2B zero][16B weights][2B scale][2B zero]... A warp accessing 32 consecutive weights (one block) reads 16 bytes, which is less than one 32-byte sector. You're wasting half the sector.

Alternatively, if you pad to 32 bytes per block: [16B weights][2B scale][2B zero][12B padding] - you're transferring padding bytes you don't need.
