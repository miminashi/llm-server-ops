**1. Why GEMV on GPU is memory-bandwidth-bound:**

GEMV: y = A * x + b, where A is M×N matrix, x is N×1 vector, y is M×1 vector.

The arithmetic intensity (FLOPs per byte) is key here:
- FLOPs: 2*M*N (multiply + add for each element)
- Bytes accessed: M*N (matrix A) + N (vector x) + M (vector y) ≈ M*N for large M

Arithmetic intensity ≈ 2*M*N / (M*N) = 2 FLOPs/byte

Compare to GEMM (matrix-matrix): A(M×N) * B(N×P)
- FLOPs: 2*M*N*P
- Bytes: M*N + N*P + M*P
- For large matrices, arithmetic intensity ≈ 2*M*N*P / (M*N + N*P + M*P) which can be hundreds or thousands of FLOPs/byte

Modern GPUs (e.g., A100, H100) have compute-to-bandwidth ratios like:
- A100: ~312 TFLOPS FP16, ~2 TB/s HBM2e → ratio ~156 FLOPs/byte
- H100: ~989 TFLOPS FP16, ~3.35 TB/s HBM3 → ratio ~295 FLOPs/byte

GEMV with intensity of 2 FLOPs/byte is WAY below the machine balance point. So the GPU's compute units sit idle waiting for data to arrive from DRAM. The bottleneck is memory bandwidth, not compute.

Additionally, in GEMV, each element of x is used exactly once per row of A. There's no reuse of x across multiple computations in the same "tile" the way GEMM has. The data is essentially "streamed" through once.

**2. Why quantization block memory layout changes effective bandwidth:**

In quantized inference (e.g., GPTQ, AWQ, or general INT4/INT8 quantization), weights are stored in compressed form. For example, INT4 quantization:
- 4 weights packed into 1 byte (or 8 weights in 2 bytes)
- Plus scale/zero-point per group (e.g., per 128 weights, there's a float16 scale and zero-point)

The memory layout matters:

- **Packed layout (column-major within groups)**: If you have a group of 128 INT4 weights, they occupy 128*4/8 = 64 bytes. The scale/zero-point might be 4 bytes (two float16). Total per group: 68 bytes. When the GPU reads a group, it reads 68 bytes but only needs 64 bytes of actual weight data. The scale/zero-point adds overhead.

- **Layout alignment**: DRAM is accessed in 32-byte or 64-byte sectors (cachelines). If quantized data isn't aligned to these boundaries, you get wasted reads. For example, if a group of 128 INT4 values (64 bytes) starts at an offset that's not 32-byte aligned, the GPU might need to fetch two 32-byte sectors to get one group's data.

- **Block size and access pattern**: If the quantization block size is, say, 128, and the GPU's memory controller fetches in 128-byte lines, then:
  - 128 INT4 values = 64 bytes of weights + scale/zero = ~68-72 bytes
  - This doesn't fill a full 128-byte cache line efficiently
  - You might get "partial line" reads where you fetch 128 bytes but only use 68

- **Interleaving vs. sequential**: If multiple blocks' data are interleaved in memory vs. stored sequentially, the access pattern changes. Sequential access allows prefetching and burst reads. Interleaved access might cause more DRAM row switches.

- **The key insight**: The "effective bandwidth" is not just the raw DRAM bandwidth. It's:
  effective_bandwidth = (useful_bytes_read) / (total_time)
  
  If you fetch 128 bytes from DRAM but only 68 are useful (the rest is padding, misalignment waste, or redundant scale/zero that was already cached), your effective bandwidth drops.

  More specifically for quantization:
  - Raw storage: INT4 → 0.5 bytes per weight
  - But with per-group scales: effective bytes per weight = 0.5 + (scale_bytes/group_size)
  - For group_size=128, scale = 2×float16 = 4 bytes: effective = 0.5 + 4/128 = 0.53125 bytes/weight
  - The "overhead ratio" = 0.53125/0.5 = 1.0625, so ~6% overhead
