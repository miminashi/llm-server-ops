**1. Why GEMV is bandwidth-bound on GPU:**

GEMV: y = A * x, where A is an M×N matrix and x is an N-dimensional vector.

- FLOPs: 2*M*N (multiply-add for each element)
- Data moved: M*N (read A) + N (read x) + M (write y) ≈ M*N bytes (assuming 32-bit floats, actually 4*M*N bytes)
- Arithmetic intensity: FLOPs / Bytes = 2*M*N / (4*M*N) ≈ 0.5 FLOP/byte (for FP32)

For GEMM (M×N × N×K), the arithmetic intensity is much higher: 2*M*N*K / (4*(M*N + N*K + M*K)) which for large dimensions becomes very high.

On a GPU like A100:
- Peak FLOPs: ~312 TFLOPS (FP32)
- Memory bandwidth: ~2 TB/s
- Ridge point: 312/2 = 156 FLOP/byte

So GEMV with ~0.5 FLOP/byte is WAY below the ridge point. The GPU has thousands of cores but the data is just too sparse relative to computation. The GPU spends most of its time waiting for data from HBM/DRAM.

Additionally:
- The vector x is small (N elements), so it can stay in cache/L2
- The matrix A is huge and must be streamed from DRAM
- The compute per element of A is just 1 multiply + 1 add (or 2 FLOPs)
- The GPU's massive parallelism (thousands of CUDA cores) can't be utilized because each thread only does a tiny amount of work per data element
- Memory latency becomes the bottleneck - you can't hide enough latency with computation

**2. Why quantization block memory layout changes effective bandwidth:**

In quantized inference (e.g., INT8, INT4 quantization), the weight matrix is stored in blocks. For example:
- Each block might be 128 elements with a shared scale/zero-point
- Or group quantization: groups of 64 or 128 elements share a scale

The "effective bandwidth" issue:

When you have quantized data, you need to:
- Read the quantized values (e.g., 4 bits per element)
- Read the scale/zero-point for the block
- Dequantize in registers: w_dequant = (w_quant - zero) * scale

The memory layout matters because:

a) **Coalescing and transaction size**: DRAM operates in fixed-size bursts (e.g., 32 bytes for HBM). If your quantized blocks are laid out such that a thread block needs to read scattered data, you get many partial transactions. For example, if 4-bit values are packed into 32-bit words, and the scale is stored separately, you might need to read the scale from a different location, breaking coalescing.

b) **Block granularity vs. memory access granularity**: If a quantization block is, say, 64 elements of 4-bit values = 32 bytes, that's exactly one cache line or one burst. But if the block is 128 elements = 64 bytes, you need two bursts. The key is whether the block size aligns with the memory subsystem's natural access granularity.

c) **Scale/zero-point placement**: If scales are stored contiguously at the end of the matrix vs. interleaved with the quantized data:
   - Interleaved: When reading a block of quantized data, the scale is right there → fewer cache misses, better locality
   - Separate: You read quantized data, then separately fetch the scale → extra memory transaction, potentially from a different DRAM bank

d) **Effective bandwidth calculation**: The "logical" data you need is N quantized values + N/block_size scales. But the "actual" DRAM traffic depends on:
   - How many DRAM bursts are triggered
   - Whether reads hit in L2/L1 or go to DRAM
   - Whether the access pattern is coalesced
   - ECC overhead
   - The ratio of useful data to total bytes transferred

e) **Specific example**: Consider INT4 quantization with group size 64.
   - 64 values × 4 bits = 32 bytes of quantized data
   - 1 scale (FP16 or FP32) = 2 or 4 bytes
