2.  **Deconstruct Each Point & Brainstorm Counterexamples:**

   *Point 1: 主張の根拠が測定に基づいているか (Are claims based on measurements?)*
   - *Concept:* Technical claims should be supported by empirical data, not just theoretical reasoning, anecdotes, or assumptions. Need to check if measurements are properly documented, reproducible, and relevant.
   - *Counterexample:* A paper claims "Algorithm X reduces latency by 40%." But the measurement setup only tested on a small, non-representative dataset (e.g., synthetic data with uniform distribution) without real-world network conditions. Or they used a stopwatch instead of precise profiling tools, leading to inaccurate timing. Or no confidence intervals/error bars are provided.
   - *Specific Example:* 「新コンパイル最適化手法により実行速度が3倍向上した」と主張するが、測定は単一のサンプルコード（ループ数が固定された単純な数値計算）で行い、計測ツールもOSの標準的な`time`コマンドのみ。実際には分岐予測ミスやキャッシュミスが頻発する実負荷では向上率が1.2倍に留まる。測定条件の限定と計測精度の不足が根拠の弱さを示す。

   *Point 2: 見落とされている交絡因子はないか (Are there overlooked confounding factors?)*
   - *Concept:* Confounding factors are variables that influence both the independent and dependent variables, causing a spurious association. In technical contexts, this could be hardware specs, software versions, environmental conditions, data preprocessing steps, etc.
   - *Counterexample:* Claiming "Feature A improves accuracy" but failing to control for dataset shift, version differences in dependencies, or hardware acceleration. For example, a machine learning paper claims a new architecture is better, but the baseline was run on CPU while the new model used GPU acceleration, or they didn't fix random seeds, so performance variation is due to initialization, not the architecture.
   - *Specific Example:* 「分散処理フレームワークYの並列化効率を2倍に改善した」という主張だが、ベンチマーク実施時にテスト環境のメモリ容量とCPUコア数が実運用環境と異なり、GC（ガベージコレクション）の頻度やOSのスケジューリング動作が測定結果に大きな影響を与えていた。また、依存ライブラリのバージョンが基盤と新規コードで異なり、最適化ルーチンの差異が「並列化効率の向上」と誤認されている可能性がある。これらの交絡因子を統制しない限り、因果関係は証明できない。

   *Point 3: 結論を出す前に必要な追加検証は何か (What additional verification is needed before drawing conclusions?)*
   - *Concept:* Based on gaps in measurement and confounding factors, what robustness checks, reproducibility tests, or extended validations are necessary? This includes cross-validation, stress testing, ablation studies, external validation, statistical significance testing, etc.
   - *Counterexample:* A paper concludes "Method Z is production-ready" based only on lab tests. Missing: long-term stability tests, failure mode analysis, compatibility with edge cases, peer replication, or statistical significance testing across multiple runs.
   - *Specific Example:* 「AI推論エンジンがメモリ使用量を40%削減できる」と結論付けているが、単一シナリオでの短時間計測のみで、長時間実行時のメモリリーク、ガベージコレクションのオーバーヘッド、異なる入力サイズでのスケーラビリティ、および他の推論フレームワークとの相互運用性評価が不足している。結論を確定させるには、(1) 複数ランの統計的有意性検定、(2) 長時間実行・高負荷状態での安定性テスト、(3) 環境変数・依存ライブラリの固定による再現性検証、(4) 外部データセットでの汎化性能評価が必要である。これらがないと「削減」は一時的な最適化或いは計測誤差の可能性が高い。
