**1. Why GPU GEMV is bandwidth-bound:**

GEMV: y = A * x, where A is an M×N matrix and x is an N×1 vector. The result y is M×1.

- FLOPs: 2*M*N (each element of y requires N multiplications and N additions)
- Bytes transferred: M*N (reading A) + N (reading x) + M (writing y) ≈ M*N for large M

Arithmetic intensity = FLOPs / Bytes = 2*M*N / (M*N) ≈ 2 FLOPs/Byte

This is extremely low. Modern GPUs have compute-to-bandwidth ratio much higher than 2. For example, an A100 has ~312 TFLOPS FP16 and ~2 TB/s bandwidth, so ratio is ~156 FLOPs/Byte. The GPU needs to do ~156 FLOPs per byte transferred to saturate compute. GEMV only gives 2, so it's massively bandwidth-bound.

In contrast, GEMM (matrix-matrix) has arithmetic intensity of 2*M*N*K / (M*K + K*N + M*N) which grows with K, easily exceeding the ratio.

The key insight: in GEMV, each element of A is used only ONCE (multiplied by one element of x). There's no reuse of the matrix elements across multiple dot products. The data must be streamed through, and the compute per byte is minimal.

**2. Why quantization block memory layout changes effective bandwidth:**

When you quantize a matrix (e.g., INT4, INT8), you pack multiple values into fewer bytes. But the layout matters:

- If you have a 4-bit quantization, you pack 2 values per byte. But how are they arranged in memory?
- If the quantization block is, say, 128 elements per scale/zero point, the layout determines:
  - Whether you can do coalesced memory access (consecutive threads reading consecutive addresses)
  - Whether you need to read the scale/zero metadata for every block
  - Whether the packed values are aligned to cache line boundaries

Specifically for GEMV with quantized weights:
- The weight matrix is stored in compressed form (e.g., INT4 instead of FP16)
- You need to read the compressed weights AND the per-block scale/zero factors
- If the block is too small (e.g., 32 elements), you read scale/zero very frequently relative to the data
- If the block is too large, you might read more data than needed for a partial computation
- The memory layout (row-major vs column-major, how scales are interleaved) affects:
  - Coalescing: if 32 threads in a warp read 32 consecutive bytes, that's one 32-byte transaction. If they read scattered bytes, you get multiple transactions.
  - The "effective" bandwidth is the useful bytes / total bytes transferred. If you read 128 bytes but only 120 are useful (8 bytes are metadata that gets re-read), effective bandwidth drops.
  - Cache line efficiency: if a quantization block spans a cache line boundary in a way that causes partial reads, you waste bandwidth.

For example, in a 4-bit quantized matrix with per-32-element scales:
- Data: 16 bytes per 32 elements
- Scale: 2 bytes (FP16) per 32 elements
- Total: 18 bytes per 32 elements
- If you naively read in 32-byte chunks, you might read 32 bytes where only 18 are the current block and 14 are the next block's data (or vice versa)
- Or if scales are stored separately, you might have to do two separate memory reads

The "effective bandwidth" = actual useful data throughput / theoretical peak bandwidth. Layout determines how much of the DRAM traffic is "waste."

- Logical bytes: the number of bytes your code "thinks" it's reading/writing (e.g., you read a 4-byte float, that's 4 logical bytes)
