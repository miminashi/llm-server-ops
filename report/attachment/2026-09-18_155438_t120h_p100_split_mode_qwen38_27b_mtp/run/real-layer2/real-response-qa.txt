**1. Why GEMV is bandwidth-bound on GPU:**

GEMV is y = A * x + b, where A is an M×N matrix and x is an N-dimensional vector.

FLOPs: 2*M*N (multiply-add for each element)
Memory access: You need to read A (M*N elements) and x (N elements). For large M, the A matrix dominates.

Arithmetic intensity = FLOPs / Bytes = 2*M*N / (M*N*sizeof(element) + N*sizeof(element))

For FP32: ≈ 2 / 4 = 0.5 FLOPs/byte
For FP16: ≈ 2 / 2 = 1 FLOP/byte
For INT8: ≈ 2 / 1 = 2 FLOPs/byte
For INT4: ≈ 2 / 0.5 = 4 FLOPs/byte

Compare to GEMM: For an M×K × K×N matrix multiply, FLOPs = 2*M*K*N, Bytes ≈ (M*K + K*N + M*N)*sizeof. Arithmetic intensity ≈ 2*K/sizeof(element) which is much higher.

GPU has massive compute (thousands of cores) but the memory bandwidth, while high (e.g., 2-3 TB/s on A100, ~1.5 TB/s on 4090), is the bottleneck when arithmetic intensity is low. The GPU's compute units will starve waiting for data. The ratio of compute to bandwidth is such that for GEMV, you're spending most of your time loading data rather than computing.

In LLM inference, the "decode" phase is essentially GEMV (batch size 1, so the input is a single vector times a weight matrix). This is why inference is bandwidth-bound while training (which uses GEMM with batch > 1) is compute-bound.

**2. Why quantization block memory layout changes effective bandwidth:**

When you quantize weights in blocks (e.g., group-wise quantization with group size 128 or 256), you store:
- Quantized weights (e.g., 4-bit or 8-bit per weight)
- Scale factors (one per group)
- Zero points (one per group, if asymmetric)

The key issue: memory layout affects how much data you actually transfer from DRAM.

Consider a weight matrix of shape [out_features, in_features] quantized with group size G.

If in_features = 4096, G = 128, you have 32 groups per row.

**Bad layout (interleaved/scattered):**
If the scale factors are stored separately from the quantized weights, or if the quantization groups are not aligned with how the GPU reads memory (e.g., not coalesced), you get extra memory transactions.

**Good layout (packed/interleaved):**
If you pack the quantized weights and their scale/zero together in a way that a single memory read (e.g., a 128-byte cache line) gives you both the quantized values and the dequantization parameters, you minimize the number of DRAM transactions.

More specifically:
- If group size is 128 and you use 4-bit quantization, 128 weights = 64 bytes. The scale might be FP16 (2 bytes) or FP32 (4 bytes). If you pack them together, a 128-byte read gets you 128 weights + scales + zeros for one group, and you can dequantize on the fly.
- If scales are stored in a separate array, you need to read both the weight array AND the scale array, potentially causing additional cache misses and DRAM accesses.

Also, alignment matters: DRAM accesses happen in units (e.g., 32-byte or 64-byte sectors, or 128-byte cache lines). If your quantized data doesn't align with these boundaries, you might fetch extra bytes that you don't need (wasted bandwidth).

Another aspect: if the group boundaries don't align with how the GPU's memory subsystem reads (e.g., a warp of 32 threads each reading one element), you might have some threads reading from one DRAM row and others from a different row, causing row activation penalties.

The "effective bandwidth" is: actual useful data / total DRAM bytes transferred. If your layout causes you to transfer 128 bytes but only use 64 bytes (because the other 64 belong to a different group's scales), your effective bandwidth is halved.
