**1. Why GEMV is bandwidth-bound on GPU:**

GEMV: y = Ax where A is an M×N matrix, x is a 1×N vector, y is 1×M vector.

FLOPs: 2*M*N (multiply-add for each element)
Bytes transferred: M*N (reading A) + N (reading x, negligible) + M (writing y, negligible)

Arithmetic intensity = FLOPs / Bytes = 2*M*N / (M*N) = 2 FLOPs/byte

Compare to GEMM: FLOPs = 2*M*N*K, Bytes = M*N + N*K + M*K, intensity ≈ 2*K (for large matrices)

GPU: Modern GPUs like A100 have ~312 TFLOPS FP16 and ~2 TB/s HBM2e bandwidth.
Roofline: 312e12 / 2e12 = 156 FLOPs/byte threshold.

GEMV has intensity of 2, which is WAY below the roofline threshold. So it's memory bandwidth limited.

The key insight: for each element of A you load, you do only 1 multiply and 1 add (2 FLOPs). The GPU's compute units are massively underutilized. You're spending most of your time waiting for data to arrive from DRAM.

Also, the vector x can often fit in L2 or even registers, but the matrix A is too large. So the bottleneck is streaming A from DRAM.

**2. Why quantization block memory layout changes effective bandwidth:**

When you quantize a matrix, you typically quantize in blocks (e.g., 1×128, 64×128, etc.). Each block has:
- Quantized weights (e.g., 4-bit or 8-bit)
- Scale factors (per block or per group)
- Zero points (if asymmetric)

The memory layout question: how are these stored?

Option A: Interleaved - [quantized_block_0, scale_0, zero_0, quantized_block_1, scale_1, zero_1, ...]
Option B: Planar/Separate - [all quantized blocks][all scales][all zeros]

Why does this matter?

- GPU memory coalescing: When threads in a warp access memory, if they access contiguous addresses, you get one transaction. If scattered, multiple transactions.

- For GEMV, you're streaming through the matrix. If quantized data and scales are interleaved in small blocks, the access pattern might be:
  - Read 128 4-bit values (64 bytes)
  - Read 1 scale (4 bytes)
  - Read 1 zero (4 bytes)
  - Read next 128 4-bit values...
  
  This creates small, non-coalesced accesses. The scale/zero reads are tiny and break the streaming pattern.

- If you separate them (planar), you can stream the quantized data in large contiguous chunks (good for coalescing), and handle scales separately (they're small, fit in registers/L1).

- Also, alignment matters: if a block of quantized data doesn't start at a 128-byte boundary (for HBM), you waste bandwidth on partial transactions.

- Another aspect: the "effective" bandwidth is not just the peak DRAM bandwidth. It's the rate at which USEFUL data arrives. If you're fetching 128 bytes but only 124 are useful (alignment waste), or if you're doing many small reads that each incur latency overhead, your effective throughput drops.

- For quantized GEMV specifically: you need to dequantize on the fly. The dequantization needs the scale. If scale is far away in memory, you need an extra load. If it's nearby (interleaved), it might come in the same cache line but you still have the coalescing issue.
