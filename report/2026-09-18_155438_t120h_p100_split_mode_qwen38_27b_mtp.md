# P100 4 枚では tensor 分割と MTP が素直に両立する

- **実施日時**: 2026年9月18日 14:29 〜 15:58 JST (ロック取り直し・tensor+MTP 起動プローブ 3 回・VRAM プリフライト・3 腕本計測 65 分・layer / layer2 の実プロンプト補正・WS 側作図とレポート作成)
- **報告日時**: 2026年9月18日 15:58 JST
- **作成者**: Claude Opus 5 (1M context)

## 概要

直前のレポートで、カード 4 枚の機械に通常型の 27B モデルを載せ、層ごとに分ける方式と一つの層を全カードで分担する方式を比べた。そのときはモデルの先読み機構（MTP）を切っていた。今回はまったく同じ条件で先読みだけを有効にして測り直した。

この比較には、もう一つ確かめたいことがあった。7 枚の別の機械で同じ実験をしたとき、分担方式だけは既定の通信ライブラリが起動時に固まるため、回避策を入れて測るしかなかった。その結果、分担方式では先読みの当たりやすさが明らかに下がり、読み込み速度も大きく失われていた。ただ、それが分担方式そのものの性質なのか回避策のせいなのかは分からないままだった。今回の 4 枚の機械では既定の通信ライブラリがそのまま動くので、回避策なしで分担方式と先読みを組み合わせた値を初めて取れる。

まず起動は 3 回とも問題なく通り、本計測も最後まで走った。先読みを足すと、生成速度は三つの構成すべてで 1.7〜2.1 倍になった。分担方式は浅いところで毎秒 48 トークンに達し、層方式の約 2.4 倍になる。先読みを切っていたときの差がそのまま残った形である。

最も大きな発見は、**分担方式でも先読みの当たりやすさがまったく下がらなかった**ことだ。合成した文章では三つの構成の採択数が一件単位まで完全に一致し、実務風の文章でも分担方式だけが低いということはなかった。したがって 7 枚の機械で見えた「分担方式では当たりにくい」という現象は分担方式の性質ではない。回避策（あるいは 7 枚という枚数）の側に原因があると考えられる。

読み込み速度も同様だった。分担方式では、先読みを足しても浅いところではほとんど落ちず、深いところで 1 割ほど落ちるだけだった。一方、層方式 4 枚は 2〜3 割落ち、これは 7 枚の機械で層方式に見えた傾向と同じである。7 枚の機械で分担方式の読み込みが大きく崩れていたのは、先読みではなく回避策のせいだった。前のレポートの切り分けを、別の角度から裏づけたことになる。

実運用に近い文章で補正すると、先読みによる生成速度の伸びは分担方式で 3〜4 割、層方式で 5〜7 割程度に縮む。それでも分担方式が層方式の 2 倍強という関係は変わらない。この機械で通常型モデルを動かすなら、分担方式と先読みを両方有効にする構成が最も速い。

次の一手としては、この機械で分担方式を回避策付き（先読みあり）でも 1 本測れば、当たりやすさの低下が回避策によるのか 7 枚という枚数によるのかを直接確かめられる。所要は 15 分ほどである。

## 前提・目的

- **背景**: [前回](./2026-09-18_131856_t120h_p100_split_mode_qwen38_27b.md)（同じ t120h-p100 ×4 / Qwen3.8-27B、**MTP 無効**）は「tensor が全面勝ち」で、残課題に「MTP 併用」を挙げていた。aws-gpu01 ×7 の [MTP 3 腕再測定](./2026-09-16_103619_aws_gpu01_split_mode_mtp_3arm.md)は、NCCL の起動ハング（0/13）を避けるため tensor 腕だけ `GGML_CUDA_ALLREDUCE=none` で測っており、「tensor では採択率が下がる」が経路の違いと交絡していた。
- **目的**: (1) 同一機・同一モデルで MTP の効果を 3 腕そろえて測る。(2) **tensor × NCCL × MTP を初めて実測し**、採択率の低下が tensor 分割そのものの性質かどうかを判定する。
- **条件の統一**: バイナリ・モデル・腕・ctx・ステージ・生成長・pp0 サイズ・KV 型・`-b/-ub` 未指定・`LAUNCH_PREFIX=""`（NCCL）はすべて前回と同一。**変更は `SPEC_ARGS` の 1 行のみ**で、値は aws-gpu01 の MTP 系列と同じ `--spec-type draft-mtp --spec-draft-n-max 2`。
- **MTP ヘッド**: モデル GGUF に同梱の `blk.64`（nextn）を使う（サーバログ `creating MTP draft context against the target model`）。サーバにある別ファイル `MTP/mtp-Qwen3.8-27B-Q4_0.gguf` は使っていない（aws 系列と同条件）。

- MTP 無効側は補正係数 1.014（前回実測）でほぼ 1 なので、無効側は合成値のまま比べている。
- **実運用でも tensor + MTP が最速**で、layer 4枚 + MTP の 2.2 倍（36.29 対 16.49）。**MTP 無効の tensor に対しても +32〜+39% 速い**（実プロンプト実測どうしでも 36.29 対 26.71 で +36%）。aws-gpu01 の `none` 経路では「回避策 + MTP が NCCL 単独にようやく並ぶ（-2〜+8%）」だったのに対し、NCCL 経路なら MTP はそのまま上乗せになる。

## 副次発見

1. **プリフライト（生成 32 トークン）の tensor decode 11.8 t/s は CUDA0 のクロック低下による見かけの値だった**。プリフライトでは tensor4 の decode が MTP 無効時（28.4 t/s）の半分以下に見え、MTP の失敗を疑った。しかし `gpu_before` / `gpu_after` を見ると、**CUDA0 だけが利用率 59〜98% なのに 405 MHz（アイドルクロック）、79℃ で張り付いていた**。tensor 分割は最も遅いカードに律速されるので、1 枚の低クロックがそのまま全体に効く。本計測の段境界では CUDA0 に 405 MHz は一度も出ず、decode も 48 t/s だった。`SW Power Capping` の累計が CUDA0 だけ 174 秒と突出していることと関係がありそうだが、原因は特定していない。**短いプリフライトの速度は信用せず、VRAM 確認だけに使うべき**。
2. **tensor + MTP + NCCL の起動は 3/3（各 15 秒）**。aws-gpu01 ×7 では MTP の有無に関係なく NCCL 起動が 0/13 だった。4 枚では MTP を足しても起動は変わらず安定している。
3. **`run-info.json` に `SPEC_ARGS` が記録されない**。投機デコードの有無は `argv-*.txt`（`--spec-type draft-mtp --spec-draft-n-max 2 --spec-draft-device …`）と、各段 JSON の `draft_n` / `draft_n_accepted` で確認した。
4. **前回セッションのロックが残っていた**。前回レポートは「ユーザ指示まで保持」としていたため、本セッション開始時に `unlock.sh` → `lock.sh` で取り直した。

## 残課題

- **採択率低下の原因を `none` 経路と枚数に切り分ける**。t120h-p100 4 枚で tensor 腕を `LAUNCH_PREFIX="env GGML_CUDA_ALLREDUCE=none"`（MTP 有効）で 1 本測る（約 15〜30 分）。採択率が下がれば原因は `none` 経路、下がらなければ 7 枚という枚数（または機種）側。同じ run で、前回残課題の「tensor 7 節の +43% が機種差か AllReduce 経路差か」にも MTP 有効条件で答えられる。
- **CUDA0 のクロック低下（副次発見 1）**。`SW Power Capping` が CUDA0 だけ 174 秒に積み上がっている。本計測の値は段境界で見る限り影響を受けていないが、tensor 分割は 1 枚の遅れに敏感なので、`nvidia-smi --query-gpu=clocks.sm,clocks_throttle_reasons.active` をサンプラに加えて常時記録したい。
- **`--spec-draft-n-max` のスイープ**。NCCL 経路の tensor は `tokens_per_cycle` 1.172 で、aws の `none` 経路（0.964）のように n_max を下げる動機は無い。むしろ合成テキストで採択率が 1.0 近くに張り付いているので、上げる方向（3〜4）を試す価値がある。
- **`start.sh` の既定**。dense モデルでは、この機械なら「tensor + NCCL + MTP」が最速構成になった。ただし既定モデル（MoE）では浅部で layer が勝つ（[MoE の計測](./2026-09-16_225707_t120h_p100_split_mode_layer_vs_tensor.md)）ので、一律の変更ではなくモデル型による使い分けが要る。また `update_and_build.sh` が NCCL を渡さない問題も先に片付ける必要がある。
- **電源とロック**: ユーザの指示により、t120h-p100 は**通電したまま、ロックは解放済み**（15:59 JST に `unlock.sh`）。`bench.local.conf` は今回の MTP 版のまま（MTP 無効版は `bench.local.conf.qwen38-27b-nomtp`、MoE 版は `bench.local.conf.qwen36-35b-a3b` に退避）。llama-server は停止済み。
