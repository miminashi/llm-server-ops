- **報告日時**: 2026年9月7日 02:20 JST

## 概要

前回の作業は、補助側のサーバが立て続けに固まったところで打ち切りになっていた。その原因はその後の調査でメモリの故障と特定され、ハードウェアの定期点検機能を止めることで回避できるようになった。今回はその状態で本来の検証を再開している。

まず上流を調べ直したところ、検証対象にしていた実装は前回から一行も進んでいなかった。同じものをもう一度測っても得るものは少ない。そこでユーザと相談し、前回の残課題として挙げていた「二つの実装を同じ機械で直接くらべる」ことを今回の主題に据えた。この二つは同じモデルに対応するための競合する実装で、どちらが本家に取り込まれるかはまだ決まっていない。速さについては、外部の報告と手元の過去の測定とで食い違う主張が出ており、決着がついていなかった。

比較は条件を徹底して揃えて行った。同じ十三枚の構成、同じ重み、同じ起動パラメータ、そして前回のセッションで保存しておいた同じ入力ファイルを使い、入力の長さだけを五段階に変えて、読み込みの速さと生成の速さの両方を測った。実装を切り替えるたびに全体を作り直しているので、二つが混ざる余地はない。念のため、片方については前回と同じ条件を最初にもう一度流し、短い入力の答えが前回と一字一句同じであること、いちばん長い入力の速度が前回と小数点以下まで同じ値になることを確かめてから本題に入っている。

結果ははっきり分かれた。入力が短いうちは片方が明確に速く、読み込みでは三割近い差がつく。ところが入力を長くしていくとこの差はじりじり縮み、いちばん長い十一万語の入力では順位が入れ替わる。読み込みでは一割強、生成にいたっては三割も、それまで遅かったほうが速くなる。つまり「どちらが速いか」という問いには、入力の長さを決めないと答えられない。用途が短い会話中心なら片方、長い文書を丸ごと読ませるなら他方、というのが今回得られた答えである。

外部から報告されていた「長い入力で片方が大きく落ち込む」という現象は、向きとしては同じだが、落ち込みが始まる場所がまるで違った。報告では三万語の時点ですでに四割落ちていたのに対し、こちらでは三万語ではほとんど落ちず、十一万語まで伸ばして初めて三割の差になる。使っているカードの世代も、重みをすべてカードに載せているか一部を主記憶に置いているかも、注意計算の実装を有効にしているかも違うので、同じ現象が違う深さで現れていると見るのが自然である。外部の報告をそのまま自分の環境の判断材料にはできない、という当たり前のことが数字で確かめられた形になる。

出力の中身も突き合わせた。短い入力では二つの実装は一字一句まで同じ答えを返し、途中の思考の文章まで完全に一致する。ところが入力が長くなると思考の文章だけが分かれ始める。答えそのものはどの長さでも正しく、深いところに埋めた合言葉もすべて言い当てているので、品質の差ではなく計算経路の差が表に出たものと見ている。

ソースを読み比べて、この違いの出どころも確かめた。二つの実装はどちらも、長い入力での計算量を抑えるための同じ発想の仕組みを持っているが、置き場所と書き方がまったく違う。片方は専用のファイルに切り出し、もう片方は既存の仕組みの中に埋め込んでいる。深いところで結果が分かれるのは、この作りの違いが積み上がった結果と考えれば筋が通る。

補助側のサーバは、この四時間半のあいだ一度も止まらなかった。四回の全体ビルドと四回のモデル読み込みという重い処理を含んでいるので、前回までの止まり方とは明らかに様子が違う。管理コントローラ側の記録にも新しいエラーは増えていない。回避策は効いていると判断してよい。

### 2. prefill (pp) — **浅いと #27754 が 28% 速く、深いと逆転する**

| プロンプト長 | #27773 (`8134115f8`) | #27754 (`629b50552`) | #27754 / #27773 |

| 16 tok | 6.0 | 9.3 | （短すぎて無意味） |

| 11,338 tok | 48.8 | **59.6** | **+22.1%** |

**優位は単調に減衰して 28k と 108k のあいだで反転する**。前回レポートおよび 09-02 レポートの「**速度を採るなら #27754 が 18% 速い**」という記述は、**32k 級までの話としては正しいが、深文脈では逆**である。

### 4. 外部報告との突き合わせ — **落ち込む深さが 1 桁違う**

PR スレッドで nicholasshirley が 1x4090 + CPU offload / `-fa off` / `-ub 1024` で報告した値と並べる。

| 深さ | #27773 (4090) | #27754 (4090) | #27773 (本環境) | #27754 (本環境) |
|---|---|---|---|---|
| 最浅 | 100% (25.3 t/s) | 100% (24.8 t/s) | 100% (9.4 t/s) | 100% (8.5 t/s) |
| 7.5k / 7.3k | 94.9% | 83.5% | 86.2% | 100.0% |
| 28.8k / 28.4k | 93.7% | **58.9%** | 87.2% | **92.9%** |
| 109.9k | 未測定 | 未測定 | **83.0%** | **70.6%** |

**「#27754 は深さで落ちる」という主張自体は本環境でも成立するが、落ち始める深さがまるで違う。** 4090 では 28.8k ですでに 41% 失っているのに対し、本環境の 28.4k はまだ 7% しか失っていない。本環境で 4090 の 28.8k と同程度（59%）まで落ちる深さは、109.9k の 70.6% から外挿してもさらに深い位置にある。

## 副次発見

- **「どちらが速いか」は深さを指定しないと意味を持たない**。7.3k で 28% 速いほうが 109.9k では 10% 遅い。**過去のレポートに残した「#27754 が 18% 速い」は 32k 級の条件付き結論**として読む必要がある
- **本環境の再現性は極めて高い**。前日の短答応答が**バイト単位で一致**し、109,917 tok の pp / tg が **28.3 / 7.8 t/s と小数点まで同値**になった。`temperature 0` と固定プロンプトを守れば、日をまたいでも比較できる
- **前回レポートの「#27773 の pooled cache が深さに強い」は、#27754 にも同等の仕組みがある点を落としていた**。#27754 は `llama-kv-cache-kpool.cpp` として専用ファイルに持っている。**差は「有無」ではなく「実装」である**
- **thinking がバイト一致する深さには境界がある**。7,349 tok までは両実装が完全に同じ思考文を出し、11,338 tok から分岐する。**実装差の検出器として thinking 長は使える**
- **prefill の累積平均は深さとともに単調に落ちる**。109,917 tok の走行中、26% 地点で 44 t/s だったものが 97% 地点で 28.8 t/s まで落ちた。**「pp は深さに依存しない」は 30k 級までの近似**である
- **ハング回避策は重負荷でも保つ**。`-j20` のフルビルド 4 回と 146 GiB のモデルロード 4 回を含む 4 時間半でハング 0 回、SEL の増加 0 件。前回は `-j40` ビルドの 50 秒後に落ちていた
- **同一モデルの 2 回目以降のロードは 3 分の 1 以下**（10 分 49 秒 → 4 分 07〜40 秒）。**ただし PR を切り替えて再ビルドしてもモデルの page cache は残る**（F1 → F2 → E2 がすべて 4 分台）

## 残課題

- **落ち込む深さが環境で違う理由の切り分け**: 本環境と 4090 の報告では `-fa` / CPU offload / GPU 世代 / `-ub` の 4 つが同時に違う。**`-fa off` で同じ 4 段階を流せば (a) を単独で切り分けられる**が、`-fa off` は attention の compute buffer が `n_ubatch × n_kv` で効くため ctx 131072 では起動できない見込み。ctx 32768 までなら可能
- **反転点の特定**: 28,390 と 109,917 のあいだで pp / tg とも逆転している。**50k / 70k 前後を 2 点測れば反転点を挟める**。1 点あたり 30〜45 分
- **#27754 の MTP を深文脈で測る**: 09-02 に 11k で tg 1.31 倍を確認しているが、**108k でも同じ倍率が出るかは未確認**。#27754 の深文脈での弱さを MTP が埋められるなら実用上の結論が変わる
- **Sparse FA が効く条件**: sm_60 で効かない理由は未切り分け（前回からの持ち越し）。`fattn-mma-f16.cuh` のどのパスが `n_kv_max` を見るのかを読めば分かる見込み
- **`--image-max-tokens` が効かない件**: 09-06 に LifesLight が報告。**mmproj の `image_max_pixels` を直接書き換えると上限が効く**とのことで、arg 側の実装漏れが疑われる。本環境には avar6 の mmproj があるので追試可能
- **#27917 (MTP for #27773)**: 依然 draft・`dirty`。未検証
- **本家マージ待ち**: #27773・#27754 とも OPEN で `mergeable_state` は `blocked` / `dirty`。**master には依然 `glm5` 系 arch が入っていない**
